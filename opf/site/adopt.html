Adopt it

Adopt OPFiles

There are two ways in. The recommended path is to let your AI development assistant do the adoption; adopting by hand is the fallback for when you cannot. Both paths target the same store format: machine-written TOML sources, generated human-readable views, and a drift gate that re-renders the views and compares them. This page walks the paths, then documents each opf command one by one, then lays out the manual steps.

Two paths

Two ways in, one store format

Assistant-driven (recommended)

Ask your AI development assistant to read the standard, inspect your project, and propose an adoption plan. Review the plan before authorizing scaffolding and validation. The standard requires no particular assistant or tool.

By hand (fallback)

Create the plain-TOML store, configure your own checks, and work records-first. The standard requires no particular tool. The reference tooling validates spec 1.2.0 stores in either layout, with limits: it does not render or drift-check per-record views, and the baseline validator reports module-tier and importer record content schemas as cannot-evaluate. For a store with module-tier or importer records, or a per-record store that declares views, doctor's overall verdict is cannot-evaluate (exit 2).

On the assistant-driven path, ask for a plan naming what to create, import, or retire and how the pieces fit together. Authorize the reviewed changes, then inspect the .working/ store, validation results, and the records-first instructions added to your project.

Provide the machine-readable /llms.txt index and /adopt.md guide as starting material. If adopting AIQT, include OPFiles and any existing operational files in the plan; review imports before applying them. You can also adopt OPFiles alone.

Command reference

The opf commands, one by one

OPFiles names a standard command vocabulary; the opf reference CLI is one implementation of it. A base adopter can use their own tooling instead, or adopt by hand. The standard and the reference suite are both a draft, so this reference documents each command by what it does at source today, except where marked Planned.

doctor distinguishes 0 clean, 1 a finding, and 2 cannot-evaluate. render --check uses exit 1 for drift; render --write and import can also exit 1 on a finding. Mutating commands can also exit 2 on a refusal or an unsuccessful operation: render --write requires passing source-integrity checks, with no internal or unattributed faults; otherwise it exits 2 and writes nothing. upgrade exits 2 when its doctor result is not VALID; after a schema rewrite, failure at render or doctor leaves the changes in place for recovery. Where a command is aimed at a directory that has not adopted OPFiles, the applicability probes (render, doctor, upgrade, absorb) report NOT APPLICABLE and exit 0. The eight commands, documented one by one below, are init, render, doctor, import, upgrade, migrate, sync, and absorb.

opf init

Purpose. Create validated source documents and a committed-store pointer for a project with no store, without git writes or rendering.

How it works. A read-only preflight runs first: it inspects the target for an existing store, an existing pointer, or foreign content already under .working/, and refuses rather than absorbing what it finds. It then builds the machine sources in memory (the manifest, the ID counters, the version ledger, the worklog, and the eleven typed indexes), writes them under .working/toml/, writes the .opf.toml pointer at the product root, and creates a CHANGELOG.md if none exists. Publication is create-only: it writes new paths and does not overwrite an existing one.

Result. A scaffolded store, a committed-store pointer, and a starter changelog if you had none, all left untracked for your review; init does not stage or commit them. See core store files for what the scaffold writes into the manifest. Publication is create-only but not transactional: a later failure can leave partial output for review. The initializer takes no lock or lease and does not serialize concurrent writers; a successful scaffold is not a whole-store validity verdict.

opf init opf init --root .

opf render

Purpose. Regenerate the store's declared views and check them against their sources, in one of two modes.

How it works. Exactly one of --check or --write is required, so a preview never turns itself into a write; a bare opf render is a usage error. --check is read-only: it re-renders every declared view from its sources and compares the bytes, reporting whether the store is clean, has drifted, or cannot be evaluated, and writing nothing. --write gates on source integrity, not on the whole-store verdict: it gathers the git-derived observations, and a drifted or missing view is its output to regenerate rather than a reason to refuse, so it rewrites the declared views from their sources. A source-integrity check that fails or reports cannot-evaluate refuses with exit 2 before writing. Planning errors can also refuse before writing; a later I/O failure can leave partial output and is reported.

Result. Under --check, a verdict and no change. Under --write, post-write validation checks source integrity and the regenerated outputs. A disagreement triggers a rollback attempt and exit 2; an incomplete rollback is reported. Other deliverable failures remain visible and can produce a nonzero exit after successful regeneration.

opf render --check opf render --write

opf doctor

Purpose. Run the whole-store integrity layer read-only and return a single verdict.

How it works. It resolves the store at the product root (or at --root DIR), gathers the git-derived observations, and runs the integrity engine over them. It makes no store change, and its report is a structured per-check verdict map, the findings and cannot-evaluates, and a residual count, never a wall of diff lines. Its coverage spans schema validity, ID uniqueness and counter monotonicity, bidirectional index reconciliation, transition legality where observations suffice, the all-or-none resolution bundle, byte drift for declared baseline views in an inline-layout store, the root VERSION deliverable (required whenever releases exist, absent before the first release), worklog span tiling and frozen digests, changelog coverage and freeze, archive integrity, the tracked-store requirement, pointer and sync-target agreement, and path containment.

Doctor reports per-record view drift and the content schemas of module-tier and importer records, including legacy_fragment, as cannot-evaluate. Baseline view coverage includes composed views and projections. A declared view outside the baseline set, such as a module-type index mirror, makes the whole drift check cannot-evaluate. Transition checks also report cannot-evaluate when legality depends on an unidentified last-transition actor or a rejection requires unavailable pre-proposal state. Doctor does not check behind, ahead, or divergence against a sync target.

Result. A valid, invalid, or cannot-evaluate verdict with the per-check breakdown, exiting 0, 1, or 2 to match.

opf doctor opf doctor --root .

opf import

Purpose. Bring an existing project's operational content into the store through a staged, reviewed, attributed flow, rather than a silent absorb.

How it works. Exactly one of four modes runs, and each requires an already-initialized store (an unresolved root is a cannot-evaluate that asks you to run opf init first). The modes chain in order:

  • --scan --set FILE: reads a declared set of sources and prints a canonical inventory to stdout; zero writes.
  • --plan --set FILE: stages a candidate run under .working/imports/<run-id>/ and prints the run id and the report path, leaving the originals in place; no live-store write.
  • --review <run-id> --actor NAME with --decisions FILE or --interactive: captures an attributed decision on every fragment and writes the acceptance record; no live-store write (a non-TTY --interactive is refused).
  • --apply <run-id>: promotes an accepted, reviewed run into the live store through a journaled, verified cutover.

Result. An inventory, a staged run id and report, an acceptance record, or a promoted store, one per mode; everything not confidently mapped is quarantined rather than dropped, and the originals stay in place until an --apply promotes a fully reviewed run. An import that promotes quarantined legacy_fragment records can succeed, but afterwards doctor reports cannot-evaluate, opf render --write refuses, and opf upgrade exits 2 without offering the change, because the baseline validator does not validate those records' content schemas. Module-tier records have the same effect. If an upgrade from 1.0.0 or 1.1.0 passes preflight, it applies the schema delta before failing at render, leaving the changes in place for recovery.

opf import --scan --set sources.toml opf import --plan --set sources.toml opf import --review R --actor "you" --decisions d.toml opf import --apply R

opf upgrade

Purpose. Apply the in-place base-schema upgrade from spec 1.0.0 or 1.1.0 to 1.2.0, staged for your own review and merge.

The schema delta for a 1.1.0 store changes only spec_version; a 1.0.0 store also receives the earlier schema delta. Declared views are then regenerated, so a stale committed view can change. Neither path creates bootstrap provenance for an existing store.

How it works. The upgrade is additive and idempotent. It resolves the store and refuses a store above the tooling's spec version. A store already at the target version returns a byte no-op if doctor is VALID, or exits 2 without writing otherwise. When migrating a 1.0.0 or 1.1.0 store, its preconditions include readable, canonical manifest and counters files matching a recognised origin shape, cleanliness over planned schema and render destinations and index collision candidates (including ignored files there), and acquisition of its single-writer lease. An untracked or ignored lease is excepted from the cleanliness check and handled separately by lease acquisition. A manifest or counters file with noncanonical formatting or comments, or a held lease, prevents that migration. It holds the lease across the change, applies the allowed schema delta as a canonical model regeneration, renders the declared views, and requires a full doctor-valid before offering the change. It never commits: you review and merge.

Result. A successful migration leaves the upgraded store uncommitted in your working tree for review and merge. A preflight refusal, including a newer-than-supported store or an older store failing the migration preconditions above, stops before writing the schema delta. A failure after the additive rewrite begins exits 2 and leaves changes already made in place. When render returns nonzero or the final doctor reports a result other than VALID, upgrade prints recovery commands using the committed HEAD, scoped to the affected store and product paths.

opf upgrade opf upgrade --root .

opf absorb

Purpose. Draft a candidate changelog entry for human curation, or compute the freeze digest of an already-curated entry, without writing files.

How it works. --covers selects unreleased (the default), a released version, or a contiguous version range. A per-release draft draws on its worklog span; a range rollup draws on the existing per-release changelog entries. --freeze-digest computes the selected curated entry's digest. Both modes validate the ledger inputs and coverage token before producing output.

Result. Draft text or a digest on stdout, diagnostics on stderr, and no store changes. Exit 0 means success or not applicable; exit 2 means cannot-evaluate. Drafts still require human curation and the reviewed publication flow.

opf absorb opf absorb --covers 1.2.3 opf absorb --covers 1.2.3 --freeze-digest

opf migrate

Status. Planned; the reference CLI currently exits 2 (not yet implemented). The following describes the standard's intended operation.

Purpose. Relocate the whole tracked store to a target location, its git history and worklog preserved, as one recorded, verified operation.

How it works. It runs under the store consistency contract and the single-writer lease, refusing to start from a stale, ahead, or divergent store. It validates the target before any push: the destination is confirmed to be the recorded, intended target rather than inherited from ambient state, so a store is not pushed to an unexpected place. It preserves the store's git history into the destination and the worklog and its archive byte for byte, and keeps the generated public deliverables (CHANGELOG.md and VERSION) in the product repository, rewiring the render targets so future renders keep writing them there. It re-points the committed pointer and the manifest's recorded sync target in the same change, then verifies the destination before retiring the source: the relocated store is cloned back and reconciled (ledgers, indexes, counters, and worklog digests) before the old location is removed or archived, and the removal is recorded.

Result. The store at its new location with the pointer, the manifest's sync target, and the actual remote in agreement; the public deliverables still in the product repository; and a worklog entry naming both the old and the new location. Migration is symmetric: in-repo to a companion repository, companion to in-repo, or anywhere to anywhere, repeatably, each move one recorded, verified, history-preserving operation.

opf migrate --store dir:../product-ops-store opf migrate --store github:acme/product-ops

opf sync

Status. Planned; the reference CLI currently exits 2 (not yet implemented). The following describes the standard's intended operation.

Purpose. Reconcile the store with its sync target, the surfaced pull-and-push step of the store consistency contract.

How it works. The consistency contract holds the store nothing-stale, nothing-ahead against its target. Where the local store is behind the target, opf sync fast-forwards it to current; where it is ahead (local commits not yet pushed, the lease still held by the resuming holder, and no divergent remote side), it pushes the pending commits as an authorized reconciliation. It runs as its own surfaced step and is not folded silently into another operation, so a pull or a push is a deliberate act you can see. A divergence (unsynced commits on two systems) is not auto-merged: opf sync surfaces it and halts for you, because a textual merge of the store's TOML records could mangle the very records the standard protects.

Result. The store reconciled to a known-consistent state with its target, fast-forwarded to current or with its pending local commits pushed, or a surfaced halt on a divergence for you to resolve by hand.

opf sync opf sync --root .

Adopt by hand

The manual path, step by step

OPFiles specifies formats, layout, naming, lifecycle, and enforcement posture, and requires no particular tool: the specification states that a project can conform with hand-maintained files and its own checks. The reference tooling validates spec 1.2.0 stores in either layout, with limits: it does not render or drift-check per-record views, and the baseline validator reports module-tier and importer record content schemas as cannot-evaluate. For a store with module-tier or importer records, or a per-record store that declares views, doctor's overall verdict is cannot-evaluate (exit 2).

The shape of the manual path is short: create the store (either run opf init to scaffold it, or write the files from the specification and schemas), commit it, generate the views with opf render --write for a supported store or your own renderer, and then work records-first. Conformance you assert by hand is self-asserted, and you should say so wherever you claim it, because no validator has checked it for you yet. The steps below fill that in.

Step 1

The minimal store

Create the machine store at .working/toml/ in your repository, with these files:

  • manifest.toml: the control document and discovery marker. It declares standard = "opf" (the exact discovery token) in its [opf] table, along with the base spec_version you conform to, the storage layout, the enforcement posture, and import_status. Register each enabled type in [types.<name>], declare [views], and supply the other tables the standard defines.
  • counters.toml: the per-namespace ID high-water marks, so an ID is never reused.
  • version.toml: the version and release ledger (numbers, dates, spans, and digests, never release prose).
  • worklog.toml: the durable operational record: one entry per change, correctable in place until a release freezes its span, never deleted. It is the exempt ledger, not a typed index.
  • Eleven typed indexes, one per baseline record type: backlog_item, done, finding, pending_decision, autonomous_decision, maintainer_decision, preference_pattern, block, handoff, reference, and contribution, each as <type>.index.toml (empty to start).

Then write the committed pointer .opf.toml at your product repository root, so the store resolves from a stable location. A [profiles.aiqt] table is optional and is ignored by base-only tooling; a base adopter need not add it.

The illustrative base [opf] table of a manifest, not a complete manifest: also register enabled types in [types] and declare views and other settings (see the standard for the normative shape, and core store files for every table it can carry):

.working/toml/manifest.toml
[opf] standard = "opf" # discovery token; exact value required spec_version = "1.2.0" # the base spec version this store conforms to layout = "inline" # "inline" or "per-record" posture = "required" # "off", "warn", or "required" (section 11) import_status = "none" # "none", "partial", or "complete"

Step 2

The layout, and the one rule of adoption

Machine source lives under .working/toml/; generated human-readable views live at .working/ top level; the curated CHANGELOG.md lives at the product repository root. A generated root VERSION is required whenever releases exist. The initial scaffold omits its view declaration; add that declaration when recording the first release so the reference renderer can produce the file. Doctor checks VERSION whenever releases exist, even if its view is undeclared.

<product repository root>/
  .opf.toml                 committed store pointer
  CHANGELOG.md              curated public changelog
  VERSION                   rendered from version.toml when declared as a view; required once releases exist
  .working/
    BACKLOG.md FINDINGS.md DECISIONS.md WORKLOG.md ...   generated views (UPPERCASE)
    toml/
      manifest.toml counters.toml version.toml worklog.toml
      backlog_item.index.toml  and its ten sibling indexes

One rule of adoption carries the whole convention: lowercase files are machine source you change through tooling or review; UPPERCASE files are generated or published deliverables you read and never hand-edit. The curated CHANGELOG.md is the one you edit, and only through its publish flow. Once the files exist, commit them, then run opf render --write for an inline-layout store (or your own generator) to produce the views from their sources.

Step 3

Working records-first

Treat the store as the source of truth: a decision, finding, or completion that is not recorded did not happen. Append a worklog entry per change; keep the backlog, findings, and decisions in their typed files; and regenerate the views rather than editing them. Typed index records carry an ID, type, status, title, timestamps, and an actor; links and captured references are optional envelope fields. An importer may omit an unknown creation timestamp with provenance. Capture references for claims that depend on external sources. IDs are never reused and records are never deleted. Worklog entries may be corrected before their span is released and are frozen afterward; post-release corrections are new linking entries. Other types follow their own lifecycles: completion receipts and autonomous decisions are immutable from creation.

Step 4

The release triad by hand

At a release, record the release and the worklog span it covers as a [[release]] row in version.toml; draft the summary from that span; curate it by hand; publish it into CHANGELOG.md; and record the freeze digest for the published entry. Old summaries can be replaced by range summaries through the reviewed rollup flow; preserve the underlying worklog entries and publication digests.

Step 5

Bring your own checks

Even before you run the reference validator, you can assert the standard's key invariants yourself. A hand adopter can check that the store is a tracked git repository (an untracked store is a hard failure, not a warning); that generated views match a fresh render; that release worklog spans tile the released worklog entries in ID order without gaps or overlaps; and that changelog summary ranges, among non-superseded summaries and excluding unreleased, tile the released versions without gaps or overlaps, with published entries unchanged since their recorded digest. These are integrity checks specified by OPFiles. Record the scope and results of your manual checks.

The honest limits

What by-hand adoption does not give you

Without the validation tooling, your conformance is self-asserted and should say so. Digest freezing and span tiling are your own discipline until a validator checks them. Some residuals are part of the standard itself and no adopter escapes them: the freeze gate cannot judge whether prose is accurate, range coverage cannot judge summary quality, and the unreleased worklog tail rests on review rather than machine freezing. The disclosure page states these limits plainly.
