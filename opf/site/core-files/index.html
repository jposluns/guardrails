The store's control and ledger files: the manifest that declares the store, the ID counters, the version ledger, the worklog (appended per change, correctable until released, then frozen), and the concurrency lease. The record indexes and the files around them follow, 1 line each.

manifest.toml

The store manifest

The store's control document and discovery marker: declarations for its schema, types, views, modules, and enforcement posture. Closed keysets throughout: an unknown key in any base section is a validation finding. The base [opf] table carries the exact discovery token standard = "opf", the spec version the store conforms to, and the homes generation. The base of a spec 2.0.0 store:

.working/toml/manifest.toml

[opf]
standard = "opf"
spec_version = "2.0.0"
homes = 2
layout = "inline"
posture = "required"
import_status = "none"

[modules]
governance = false

Note

The reference tooling does not yet implement spec 2.0.0: its scaffold still writes spec_version = "1.2.0" with no homes key.

The top-level tables

11 tables

The top-level tables of the store manifest
TableHolds
[opf] standard, spec_version, homes (2), layout (inline | per-record), posture (off | warn | required), import_status (none | partial | complete)
[store]sync_target (empty under the in-repo default)
[modules]governance, delivery_assurance, operational_policy, concurrent_operation
[profiles.*]additive requirement bundles; may only add requirements
[types.*]1 table per enabled type, carrying its normative namespace
[providers.*]handler and roles (create, auth, sync); local-directory and generic-git-remote ship as universal fallbacks
[views.*]kind (deterministic, composed or projection), sources, target
[deliverables.*]the curated CHANGELOG.md declaration
[archive]period ("year")
[unmanaged]pre-existing files kept in place, enumerated
[vendors]registered x-<vendor> extension namespaces

Declare the store contract so tools need not infer it.

A tool validates the base before operating, enforces only what is declared, and records a profile it does not support as present-but-unevaluated rather than failing over it. Tooling locates the machine store by finding exactly 1 immediate subdirectory of .working/ whose manifest declares the token. 0 matches or more than 1 stops the tool, never guesses.

counters.toml

The ID counters

The ID authority: 1 monotonic high-water value per record namespace.

version.toml

The version ledger

The version and release ledger: numbers, dates, spans, and digests, never release prose.

worklog.toml

The worklog

The detailed operational record: 1 entry per change, appended as the work happens. Entries are correctable until released, then frozen.

lease.toml

The single-writer lease

Present only while a run holds the store's single-writer lease; its absence is the normal state.

Record indexes

The backlog

11 baseline typed indexes, their declared generated views, and the planned module schemas. One record per unit of planned work, with a permanent ID, a closed set of states, and a "done" that is ratified.

Completion receipts

A durable completion receipt, created in its single terminal state and immutable from birth.

The finding register

An observation worth acting on, which links its remediation rather than containing it.

Pending decisions

A question that must be answered before dependent work settles.

Self-made decisions, on the record

A call an actor was authorized to make itself, with its basis, the action taken, and links to what it affected.

Rulings the maintainer made

A created-terminal, immutable ruling carrying its decision, the answer plus its rationale.

Standing preferences, distilled

The reusable rule beneath a family of individual rulings.

Blocks

A record that named work cannot proceed; it scopes an enumerated list of record IDs.

The session handoff

The durable state snapshot a session resumes from, with at most 1 current handoff at any time.

Sources, captured at the claim

An immutable captured source, recorded at the moment a claim or artefact that rests on it is produced.

Work proposed or sent to a peer project

It tracks proposal, delivery, and outcome.

Optional modules and importer types

4 optional modules, default-off.

Around the records

The store pointer

The committed pointer that names where the store repository lives. A pointer that does not resolve stops the tool and never falls back silently to the default location.

The archive

1 rotation manifest per calendar-year bucket: rotation is relocation, never deletion, and never ID reuse.

The decisions projection

The machine projection, generated at .working/DECISIONS.toml and rendered from the 4 decision types.
