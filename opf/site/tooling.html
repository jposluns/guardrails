Reference tooling

Reference tooling

OPFiles names a standard command vocabulary; the reference suite implements that vocabulary: seven commands to create, render, validate, upgrade, import, relocate, and synchronize a store.

Status

Status

The standard is a draft, and so is the reference suite below. A base adopter can use their own tooling instead, or adopt by hand. The turnkey walkthrough, a start-to-finish sequence with real command output, is a future section of this page: it will be written only from an observed run, never transcribed from design intent.

Commands

The command vocabulary

opf init

Scaffolds validated store sources and the committed pointer; surfaces, never absorbs, anything already at the store location.

opf render

Regenerates the declared views; --check reports drift read-only, --write writes only on a full store validation before and after.

opf doctor

Runs the whole-store integrity layer read-only and returns a valid, invalid, or cannot-evaluate verdict.

opf upgrade

Applies the in-place, additive, idempotent base-schema upgrade, staged for your own review and merge; it never commits.

opf import

Scans, plans, captures attributed reviews of legacy content, and promotes a reviewed import with --apply.

opf migrate

Relocates the whole store, git history and worklog preserved, to any location a target can name.

opf sync

The surfaced pull and push step of the store consistency contract.

Coverage

What the tooling checks

When it runs, opf doctor covers the integrity layer:

Schema validity ID uniqueness and counter monotonicity Bidirectional index reconciliation Transition legality The all-or-none resolution bundle Byte drift for every deterministic view Worklog span tiling and frozen digests Changelog coverage and freeze Archive integrity The tracked-store requirement Pointer and sync-target agreement Path containment

At the strictest posture, an unreadable, unparseable, or unresolvable declared input is a failure, never an empty or clean result.

Integrity

Trust and integrity

The release digests are published now, independently of artefact delivery, at posluns.dev/hashes.txt, so you can confirm that the tooling you downloaded matches the one we intended to publish. Before applying anything, verify the pack's published digest against the authoritative reference on posluns.dev, and refuse on a mismatch or missing evidence.

Publishing a verifiable signature alongside releases is a roadmap item.

Discovery

How an assistant finds the standard

The site exposes a machine-readable entry point for AI assistants: an /llms.txt index, a machine-readable /adopt.md, and a plain link on the root page an assistant can follow, so pointing an assistant at the site is enough for it to find and follow the adoption steps.

Relationship

Relationship to the reference suite

This tooling is part of the AIQT Guardrails reference enforcement suite. It is a consumer of the standard, not its definition: a base adopter can use their own tooling, or adopt by hand (see adopt by hand), and still align with the specification using their own checks. The standard defines the store and the command vocabulary; the reference implementation is one way to work them.
