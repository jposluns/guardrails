Reference tooling

Reference tooling

OPFiles names eight command verbs: init, import, doctor, render, migrate, sync, upgrade, and absorb. The reference CLI implements six; migrate and sync are planned and currently exit 2 (not yet implemented).

Status

Status

The standard is a draft, and so is the reference suite below. A base adopter can use their own tooling instead, or adopt by hand. The turnkey walkthrough, a start-to-finish sequence with real command output, is a future section of this page: it will be written only from an observed run, never transcribed from design intent.

Commands

The command vocabulary

opf init

Scaffolds validated store sources and the committed pointer; surfaces, never absorbs, anything already at the store location.

opf render

Regenerates declared views. --check compares bytes read-only. --write gates on source integrity, then checks source integrity and regenerated outputs after writing; other deliverable failures can remain and cause a nonzero exit.

opf doctor

Runs the whole-store integrity layer read-only and returns a valid, invalid, or cannot-evaluate verdict.

opf upgrade

Applies the in-place, additive, idempotent base-schema upgrade, staged for your own review and merge; it never commits.

opf import

Scans, plans, captures attributed reviews of legacy content, and promotes a reviewed import with --apply.

opf absorb

Drafts changelog entries for human curation or computes a curated entry's freeze digest; outputs to stdout without writing files.

opf migrate

Planned: relocate the whole store, preserving git history and worklog. Not yet implemented in the reference CLI (exit 2).

opf sync

Planned: the surfaced pull and push step of the store consistency contract. Not yet implemented in the reference CLI (exit 2).

Coverage

What the tooling checks

When it runs, opf doctor covers the integrity layer:

Schema validity ID uniqueness and counter monotonicity Bidirectional index reconciliation Transition legality where observations suffice The all-or-none resolution bundle Byte drift for every declared view (inline layout) Worklog span tiling and frozen digests Changelog coverage and freeze Archive integrity The tracked-store requirement Pointer and sync-target agreement Path containment

Doctor reports per-record view drift and the content schemas of module-tier and importer records, including legacy_fragment, as cannot-evaluate. Transition checks also report cannot-evaluate when legality depends on an unidentified last-transition actor or a rejection requires unavailable pre-proposal state. Doctor does not check behind, ahead, or divergence against a sync target.

At the strictest posture, an unreadable, unparseable, or unresolvable declared input is a failure, never an empty or clean result.

Integrity

Trust and integrity

Before applying a downloaded pack, compare its digest with the independently published reference at posluns.dev/hashes.txt for that release. Refuse on a mismatch or missing evidence; the presence of this instruction does not establish that a reference is currently available.

Publishing a verifiable signature alongside releases is a roadmap item.

Discovery

How an assistant finds the standard

The site provides an /llms.txt index and /adopt.md guide, also linked from the root page. Ask your assistant to read them, inspect your project, and propose a plan for review.

Relationship

Relationship to the reference suite

This tooling is part of the AIQT Guardrails reference enforcement suite. It is a consumer of the standard, not its definition: a base adopter can use their own tooling, or adopt by hand (see adopt by hand), and still align with the specification using their own checks. The standard defines the store and the command vocabulary; the reference implementation is one way to work them.
