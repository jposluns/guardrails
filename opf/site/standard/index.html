The standard

The specification, and how to read it

OPFiles is defined by a written specification. The canonical specification and quickstart are the Markdown source in the repository, linked here directly.

Scope

The standard requires a tracked git store and a review flow. Schema and drift checks are intended to catch structural defects; review recorded claims against their evidence. migrate and sync are specified, not yet implemented; upgrade and import refuse with exit 2. opf adopt cannot finish yet: apply refuses every plan and complete refuses with exit 2. The reference tooling initializes stores at base 1.2.0; it does not yet implement base 2.0.0.

Read OPF-SPEC.md (opens in a new tab); read the quickstart (opens in a new tab).

Coverage

What the specification defines

  • Store layout and naming
  • Pointer and discovery model
  • Git-repository and migration rules
  • Release triad and its gates
  • Record model and status grammar
  • The manifest and profiles
  • Views and the closed transform vocabulary
  • Enforcement posture
  • Rotation, archive, and retention
  • History, frozen digests, index reconciliation, and archive enumeration
  • Adoption and post-adoption import
  • The genericization boundary
  • The conformance vocabulary
  • Residual-coverage disclosures

Conformance

Conformance language

Conformance language follows common standards practice; statements without these keywords are descriptive.

Conformance language
KeywordMeaning
MUSTAn absolute requirement.
MUST NOTAn absolute prohibition.
SHOULDA strong recommendation, departed from only for a recorded reason.
MAYGenuinely optional.

Draft status

Draft status and self-asserted conformance

Rule

The specification is a working draft and the reference tooling lands verb by verb. Until the validation tooling covers a given claim, conformance to that claim is self-asserted, and a report says so: an unqualified "conformant" claim is never emitted, by tooling or by prose.

The specification is dated 2026-10-24.
